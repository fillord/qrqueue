# Frontend — шаг 7 (Web Push, прогноз ожидания)

Что реализовано в этом шаге (см. `ARCHITECTURE.md`, разделы 2 push_subscriptions, 5 Реальное
время, 6 Public, 7, 9 шаг 7):

## Бэкенд

- `app/services/notifications.py` — `send_push(db, subscription, payload)` через `pywebpush`
  (синхронная библиотека, вызывается через `asyncio.to_thread`, чтобы не блокировать луп);
  best-effort — `404`/`410` от push-сервиса удаляет протухшую подписку и логирует, любая другая
  ошибка (включая не-`WebPushException`) только логируется, ничего наружу не пробрасывается. Если
  `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` не заданы — тихо ничего не делает. `subscribe`/`unsubscribe`
  — апсерт/удаление `push_subscriptions` по `endpoint` (уникален сам по себе, поэтому повторная
  подписка того же браузера просто перепривязывает строку к текущему `client_id`, а не падает на
  уникальном ограничении).
- `POST /public/push/subscribe {endpoint, keys}`, `DELETE /public/push/unsubscribe {endpoint}`,
  `GET /public/push/vapid-key` — новый эндпоинт из этого шага, отдаёт `VAPID_PUBLIC_KEY` как есть
  (пустую строку, если не настроен).
- Хук в `services/tickets.py`, только в `call_next()` (best-effort, после `commit`+`publish`,
  в своём `try/except`, никогда не роняет переход талона):
  - `_notify_called` — пуш владельцу вызванного талона («Вас вызывают — A-001» / «Подойдите к
    Кабинет 3.»), если у талона есть `client_id` и подписки.
  - `_notify_approaching_position` — берёт первые 3 `waiting`-талона очереди; если третий ещё не
    отмечен (`tickets.position_notified`), шлёт ему пуш и ставит флаг. Проверялось только через
    `call_next` (как и просили) — не через `return_to_queue`/другие переходы, которые тоже двигают
    позиции, но явно не были в списке.
  - Новая колонка `tickets.position_notified bool not null default false` — миграция
    `78180560d744` (автосгенерирована, вручную добавлен `server_default` на время бэкафилла
    существующих строк, чтобы `NOT NULL` не упал на непустой таблице, и снят сразу после — модель
    сама всегда передаёт `False` для новых строк).
- `app/services/wait_estimate.py: estimate_wait_seconds(db, queue, organization, now=None)` —
  среднее `finished_at - serving_started_at` по последним 20 `served`-талонам этой очереди **за
  сегодня** (в таймзоне организации); `None`, если таких меньше 5. `build_ticket_detail` теперь
  считает `estimated_wait_seconds = среднее × позиция` для `waiting`-талонов (иначе `null`) —
  поле в `TicketDetailOut` переименовано из неиспользовавшегося `estimated_wait_minutes`.

## Фронтенд

- `src/sw.ts` — service worker: `push` → `showNotification` с `title`/`body` из пейлоада,
  `notificationclick` → фокус уже открытой вкладки `/t/:id` этого талона или `openWindow`, если
  такой вкладки нет. Собирается отдельным входом в `vite.config.ts` (без хэша, `/sw.js` в корне —
  так и регистрируется) — единственный файл в проекте с `// @ts-nocheck`
  (`ServiceWorkerGlobalScope` конфликтует с `DOM` lib остального приложения; заводить вторую
  tsconfig-конфигурацию ради дюжины строк не стал).
- `src/app/App.tsx` — регистрирует `/sw.js` при загрузке (`registerServiceWorker()` из
  `lib/push.ts`, no-op на несовместимых браузерах — `isPushSupported()` проверяет
  `serviceWorker`/`PushManager`/`Notification` до любых действий).
- `/t/:id` (`components/PushOptInBanner.tsx`) — ненавязчивая плашка, только пока
  `Notification.permission === 'default'` и API поддерживается; кнопка «Включить уведомления» →
  `GET vapid-key` → регистрация SW (на случай если ещё не успела) → `pushManager.subscribe()` →
  `POST /push/subscribe`. Отказ, неподдерживаемый браузер, не настроенный на бэкенде VAPID-ключ —
  везде просто скрывает плашку, ничего не ломает.
- `/t/:id`, статус `waiting`: «Примерное время ожидания: ~N мин» из `estimated_wait_seconds`, если
  не `null` — никогда не выдумывает число сама.
- Строки — новые `ticket.push.*` и `ticket.waitEstimate` на kk/ru/en.

## VAPID-ключи

`.env.example` намеренно пустой — сгенерировать один раз и вставить в свой `.env`:

```bash
npx web-push generate-vapid-keys
```

Публичный ключ → `VAPID_PUBLIC_KEY`, приватный → `VAPID_PRIVATE_KEY` в `.env`. `VAPID_SUBJECT`
можно оставить `mailto:admin@example.com` из `.env.example`. Без ключей всё остальное работает как
раньше — `GET /push/vapid-key` просто отдаёт пустую строку, и плашка на `/t/:id` никогда не
показывает рабочую кнопку подписки (сама плашка тоже не отрисуется — нет смысла звать её,
подписаться всё равно не выйдет).

## Ручной сквозной тест

Нужны реальные VAPID-ключи (см. выше) в `.env`, иначе плашка подписки не появится — остальной
сценарий (кроме самого пуша) при этом всё равно проверяем.

1. Поднять стек с настоящими VAPID-ключами, создать организацию/админа/оператора/очередь — как
   раньше.
2. **Клиент разрешает уведомления**: отсканировать `/q?t=<token>` с телефона или в обычном окне
   браузера на этом же компьютере (push на localhost из настоящего браузера desktop-Chrome
   работает без HTTPS-туннеля; с отдельного телефона к `localhost` разработческой машины не
   достучаться — для этого нужен туннель вроде ngrok или тестовый HTTPS-домен, здесь не
   настраивали) → на `/t/:id` нажать «Включить уведомления» → разрешить в браузерном диалоге.
3. **Второй талон продвигается до позиции 3**: отсканировать тот же токен ещё 3 раза в других
   окнах/вкладках (разные `qc`-cookie — 4 талона всего), затем оператором вызвать первый
   (`/operator/queue`, «Вызвать следующего») — второй талон становится третьим в очереди.
4. **Push приходит даже при свёрнутой вкладке**: свернуть/переключить вкладку со вторым талоном —
   системное уведомление «Скоро ваша очередь — …» должно появиться (на localhost в Chrome работает
   и в фоне, если сам браузер запущен; если он полностью закрыт — доставка зависит от ОС/браузера
   и уже не гарантируется даже в проде). Клик по уведомлению разворачивает/фокусирует именно
   вкладку с этим талоном.
5. Затем оператор вызывает второй талон (`«Вызвать следующего»` после `finish` первого) — на его
   `/t/:id` тоже приходит push «Вас вызывают — …», и в браузере, и (если разрешение уже было дано)
   как системное уведомление.
