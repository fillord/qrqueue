# Frontend — шаг 9, часть 3 (UI суперадмина: организации, админы, табло)

Что реализовано (см. `ARCHITECTURE.md`, раздел 6 Admin/Superadmin):

## Бэкенд

Ничего не менялось — не потребовалось. Всё, что нужно, уже было:

- `GET/POST /sa/organizations`, `PATCH /sa/organizations/{id}` (в т.ч. `is_active`),
  `GET/POST /sa/organizations/{id}/admins`, `PATCH .../admins/{admin_id}` — уже существовали с
  шага 1/2, просто без фронта.
- **tv-screens для любой организации (пункт 3 задания)** — выбрал вариант «расширить
  `/admin/tv-screens` параметром `organization_id`», не отдельный `/sa/.../tv-screens`. Причина:
  все `/admin/*`-роуты уже проходят через `current_organization_id`
  (`app/api/deps.py`), которая для `superadmin` **уже** резолвит организацию из
  `?organization_id=` в query, а для `org_admin` — берёт `user.organization_id` и игнорирует
  параметр. Значит `POST/GET/DELETE /admin/tv-screens?organization_id=<id>` от суперадмина работает
  уже сейчас, без единой строки на бэкенде — ровно то же самое, чем уже пользуются `/sa/analytics`
  и `/sa/audit-logs`. Отдельный `/sa/.../tv-screens` создавал бы дублирующий роут ради того, что
  и так работает.

## Фронтенд

- **`/sa/organizations`** (`SaOrganizationsPage`) — таблица организаций (название со ссылкой на
  карточку, slug, тариф, статус). Создание — `OrganizationFormModal` (название, slug
  необязательно — бэкенд сам генерирует через `generate_unique_slug`, ничего не выдумывал).
  Деактивация/активация — кнопка, переключает `is_active`, как везде в системе.
- **`/sa/organizations/:id`** (`SaOrganizationDetailPage`) — шапка (название, статус, slug,
  тариф), ссылки «Аналитика этой организации» → `/sa/analytics?organization_id=<id>` и «Журнал
  этой организации» → `/sa/audit-logs?organization_id=<id>` (сами эти страницы, уже готовые с
  шага 8, теперь читают `organization_id` из query через `useSearchParams` и подставляют его в
  фильтр организации при первом рендере — «переиспользуй» в буквальном смысле, ни одной новой
  страницы аналитики/журнала). Ниже — список админов организации (имя, email, статус),
  создание (`AdminFormModal`: имя, email, пароль — роль всегда `org_admin`, выбора нет), деактивация
  /активация. В самом низу — управление TV-экранами этой организации: `AdminTvScreensPage`
  (тот же компонент, что и `/admin/tv-screens` у org_admin с шага 5) теперь принимает
  необязательный проп `organizationId` — если передан, все вызовы (`getTvScreens`,
  `createTvScreen`, `deleteTvScreen`, список очередей для привязки) идут с
  `?organization_id=<id>`; без пропа (обычный `/admin/tv-screens`) ведёт себя как раньше, для
  org_admin. Один компонент на два контекста вместо copy-paste.
- **Боковое меню `/sa`** (`SaLayout`) — «Организации» / «Аналитика» / «Журнал». Заглушки не
  было — раньше пунктов «Организации» в меню просто не было вообще.
- Ошибки создания/деактивации — тосты через уже существующие `useToasts`/`ToastStack` и
  `lib/apiError.ts: apiErrorMessage()` (404/409/422 → понятный текст на языке интерфейса), как в
  `/admin/queues`/`/admin/cabinets`/`/admin/users` из первой части шага 9. Новые строки —
  `admin.saOrganizations.*` — на kk/ru/en; там, где смысл совпадает с уже существующими ключами
  (имя/email/пароль в форме админа, «активен»/«деактивировать» и т.д.) — переиспользованы
  `admin.users.*`, не задублированы.

## Ручной сквозной тест

Проверено вручную прямыми HTTP-запросами теми же payload'ами, что шлют новые формы (см. `git log`
этого шага), плюс визуально через `docker compose up`:

1. Войти **superadmin** → `/sa/organizations` → «Создать организацию»: только название, slug
   не указывать → организация появляется в списке со сгенерированным slug, тариф «Пробный»,
   статус «Активен».
2. Открыть карточку организации → «Добавить админа»: имя/email/пароль → админ появляется в списке
   со статусом «Активен».
3. Разлогиниться, войти под этим новым админом → `/admin/queues`, `/admin/cabinets`,
   `/admin/users` — везде пусто (только что созданная организация действительно с нуля, ничего не
   унаследовала).
4. Вернуться суперадмином на карточку организации → в блоке «Экраны (ТВ)» создать экран без
   привязки к очереди → в таблице появляется строка с `pairing_code` (6 цифр) — тот же
   компонент, что и `/admin/tv-screens`, просто в контексте чужой организации.
5. На карточке — ссылка «Аналитика этой организации» уводит на `/sa/analytics` с уже выбранной
   в фильтре этой организацией (не «Все организации»); то же для «Журнал этой организации».
6. Деактивировать админа на карточке организации — статус меняется на «Деактивирован»; повторный
   вход под его email/паролем → 401. Деактивировать саму организацию в `/sa/organizations` —
   статус тоже меняется, запись никуда не удаляется.
