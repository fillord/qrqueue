# Frontend — шаг 8 (аналитика и журнал действий)

Что реализовано в этом шаге (см. `ARCHITECTURE.md`, разделы 2 audit_logs, 6 Admin/Superadmin, 7,
9 шаг 8):

## Бэкенд

- `app/services/analytics.py: get_analytics(db, *, organization_id, timezone_name, date_from,
  date_to, queue_id=None)` — по одному SQL-проходу на группу метрик (без N+1):
  - агрегат с `FILTER`-клаузами: среднее время ожидания (`called_at − created_at`), среднее время
    приёма (`finished_at − serving_started_at`) по `served`-талонам, средняя оценка и число
    оценок, счётчики `served`/`no_show`/`left`, доля неявок `no_show / (served + no_show + left)`;
  - `GROUP BY` по оператору (`called_by`): число принятых и среднее время приёма на оператора,
    джойн на `users` для имени;
  - `GROUP BY` по часу создания талона (0–23, часы без данных — явные нули) и по дню недели
    (`EXTRACT(ISODOW …) − 1`, приведено к принятому в `queue_schedules.weekday` 0=пн…6=вс) — оба
    через `func.timezone(tz_name, created_at)`, то есть в таймзоне организации, а не UTC.
  - `organization_id=None` — специальный режим «все организации» (только для superadmin без
    выбранной организации), в этом случае группировка по часам/дням идёт в UTC.
- `app/services/audit_query.py: list_audit_logs(db, *, organization_id, date_from, date_to,
  action, limit, offset)` — постраничная выборка `audit_logs` (сортировка `created_at desc`) +
  отдельный `count`-запрос; `outerjoin` на `users` для отображаемого имени, когда
  `actor_type == user`; `ip` явно приводится к `str()` — asyncpg отдаёт `INET` как
  `ipaddress.IPv4Address`/`IPv6Address`, а не строку.
- `GET /api/admin/analytics?from&to&queue_id?` — org_admin, org берётся из токена;
  `GET /api/admin/audit-logs?from&to&action?&limit&offset` — тоже org_admin, org_id всегда
  проставлен неявно (даже без фильтров нельзя увидеть чужую организацию).
- `GET /api/admin/organization` — маленькое добавление сверх заявленного: без него `PATCH` было
  бы невозможно заполнить формой текущими значениями на фронте.
- `GET /api/sa/analytics` и `GET /api/sa/audit-logs` — то же самое для superadmin, но без org_id
  в токене: `organization_id` — необязательный query-параметр; без него аналитика/журнал строятся
  по всем организациям сразу (таймзона UTC), с ним — как у org_admin, плюс `queue_id` из чужой
  организации при выбранной `organization_id` тоже даёт 404 (сущность не найдена в этой
  организации, не 403).
- Тесты: `test_analytics.py` (корректность чисел на талонах с известным таймингом, пустой диапазон
  дат → нули/`null`, а не 500, изоляция по организации даже через `queue_id` чужой организации →
  404, superadmin «все организации» vs «одна организация»), `test_audit_logs.py` (фильтр по
  `action`, фильтр по датам, org_admin видит только свою организацию даже без фильтров,
  `actor_name` из джойна, superadmin со/без `organization_id`).

## Фронтенд

`/admin` стал настоящей панелью со сайдбаром (`AdminLayout`) вместо заглушки:

- **Аналитика** (`AdminAnalyticsPage`, `/admin/analytics`) — диапазон дат (по умолчанию последние
  7 дней), необязательный фильтр по очереди, карточки (среднее ожидание, среднее время приёма,
  доля неявок, средняя оценка), два столбчатых графика (пики по часам и по дням недели) и таблица
  по операторам. Графики — `components/BarChart.tsx`, обычный `<canvas>` без библиотек (в проекте
  и так только `react-router-dom` и `i18next`, новых зависимостей не добавлялось), цвета берёт из
  CSS-переменных темы, перерисовывается по `ResizeObserver`.
- **Журнал действий** (`AdminAuditLogPage`, `/admin/audit-logs`) — фильтры по действию и датам,
  таблица, пагинация (25 на страницу), время показывается в таймзоне организации
  (`getOwnOrganization().timezone`, `lib/formatDate.ts`).
- **Организация** (`AdminOrganizationPage`, `/admin/organization`) — форма настроек (название,
  логотип, цвет бренда, язык по умолчанию, таймзона, один активный талон на организацию),
  сохраняется через существующий `PATCH /admin/organization`.
- **Очереди / Кабинеты / Персонал** — оставлены заглушками `InDevelopmentPage` с пометкой
  «шаг 9»: фронта для управления ими ещё нет, реализовывать его в этом шаге не входило в задачу.
- **Экраны (ТВ)** — существующая страница из шага 5, просто добавлена в сайдбар.

`/sa` получил такой же, но заметно более узкий набор (`SaLayout` — вкладки, не полноценный
сайдбар: управление организациями/админами уже доступно через API с шага 1/2, но своего фронта не
получало и в этом шаге тоже не получает):

- **Аналитика** (`SaAnalyticsPage`, `/sa/analytics`) — те же карточки/графики/таблица, плюс
  селектор организации (`GET /api/sa/organizations`); без выбранной организации показывает
  агрегат по всем сразу и подсказку под фильтрами; выбор очереди появляется только после выбора
  организации (`getAdminQueues(organizationId)`).
- **Журнал** (`SaAuditLogPage`, `/sa/audit-logs`) — то же самое с колонкой организации и
  селектором; таймзона — организации (если выбрана) или локальная браузерная как запасной
  вариант.

`AuthContext`/`roleHome.ts`: редирект после входа — `org_admin` → `/admin/analytics`,
`superadmin` → `/sa/analytics` (было на голые `/admin`/`/sa`-заглушки).

Новые строки — `admin.nav.*`, `admin.organization.*`, `admin.analytics.*` (включая
`weekdays.*`/`columns.*`), `admin.auditLog.*` (включая `actorType.*`/`columns.*`),
`admin.saAnalytics.*`, `placeholder.stepNote` — на kk/ru/en.

## Ручной сквозной тест

1. Поднять стек, создать организацию/org_admin/оператора/очередь/кабинет — как раньше (через
   superadmin-эндпоинты или напрямую в БД).
2. Пройти обычный сценарий из шагов 3–5: отсканировать QR несколько раз (создать талоны),
   оператором вызвать/принять/завершить часть из них (`/operator/queue`) — это одновременно
   создаёт данные для аналитики и записи в журнал (`ticket.created`, `ticket.called`,
   `ticket.serving_started`, `ticket.finished`, `user.login` и т.д.).
3. Войти как **org_admin** (`/login`) — после входа сразу попадаем на `/admin/analytics`.
   Карточки показывают реальные среднее время ожидания/приёма, долю неявок; график «Пики по
   часам» отмечает час, в который были созданы талоны; таблица «По операторам» показывает того
   же оператора, что вызывал талоны на шаге 2.
4. Перейти в «Журнал» (`/admin/audit-logs`) — видна история действий из шага 2 в обратном
   хронологическом порядке, с именем оператора там, где он был актором, и меткой «Система»/
   «Посетитель» — где нет. Фильтр по действию (например, `ticket.called`) сужает список; фильтр
   по датам работает так же.
5. Выйти, войти как **superadmin** — попадаем на `/sa/analytics`. Без выбранной организации видно
   агрегат по всем организациям сразу; выбрав ту же организацию из шага 1 — те же цифры, что видел
   org_admin на шаге 3, плюс появляется фильтр по очереди.
