# Frontend — шаг 9, часть 1 (UI очередей, кабинетов, персонала)

Что реализовано в этой части шага 9 (см. `ARCHITECTURE.md`, разделы 2, 3, 6 Admin/Superadmin, 7):

## Бэкенд

Основные CRUD для очередей/кабинетов/персонала существуют с шага 2 и не менялись. По ходу
реализации UI обнаружились три пробела — все три согласованы с пользователем перед правкой,
backend не трогался «на ходу»:

- **`GET /admin/queues` теперь отдаёт `waiting_count`** — число `waiting`-талонов на очередь
  прямо в списке. Раньше этого поля не было нигде в admin-API. Реализовано одним `GROUP BY`
  запросом (`services/queues.py: list_queues_with_waiting_counts`), без N+1 по очередям.
- **`GET /admin/cabinets/{id}/operators`** (новый) — списка назначенных операторов кабинета не
  было вообще, только `POST`/`DELETE` для назначения. Добавлен маленький read-only роут
  (`services/cabinets.py: list_cabinet_operators`).
- **`GET /admin/queues/{id}/schedule`** (новый) — был только `PUT` (перезапись расписания
  целиком), так что редактор расписания не мог предзаполнить форму текущими днями.
  `ScheduleEntryOut` уже существовал в схемах, но не использовался ни одним роутом.

Отдельно — реальная правка поведения, тоже согласованная отдельно, а не решённая самостоятельно:
**ручная пауза очереди админом теперь «липкая», как `closed`.**

Раньше `PATCH /admin/queues/{id} {status: paused}` был обычной перезаписью поля без всякой связи
с кабинетами. Но `_sync_queue_status_after_cabinet_change` (срабатывает при паузе/резюме кабинета
оператором) пересчитывает `queue.status` из статусов кабинетов на этой очереди — и если админ
поставил `paused`, а потом оператор просто нажал «Возобновить» на своём (по другой причине
поставленном на паузу) кабинете, очередь тихо переоткрывалась, отменяя решение админа. Для
`closed` эта проблема не возникает — синхронизация с кабинетами вообще пропускает закрытые
очереди. Починка: новая колонка `queues.manually_paused` (миграция `9fe4fe679793`, backfill
существующих `paused`-очередей) — `true`, только когда `paused` выставлен админом через `PATCH`
(`services/queues.py: update_queue`), не через каскад от кабинетов. Пока флаг `true`,
`_sync_queue_status_after_cabinet_change` не переоткрывает очередь — но каскадная пауза «все
кабинеты пула встали на паузу → очередь paused» и обратное автопереоткрытие для этого случая
(когда паузу вызвали именно кабинеты, а не админ) работают как раньше, не превращаясь в залипание.

Тесты (`test_admin.py`): `waiting_count` в списке очередей на известных данных, липкость
admin-паузы против `resume` кабинета (полный цикл: admin pause → operator pause+resume своего
кабинета → очередь всё ещё paused → admin возвращает open), список операторов кабинета,
round-trip расписания (`PUT` → `GET`).

## Фронтенд

`/admin` получил три новых раздела вместо заглушек «шаг 9»:

- **`/admin/queues`** — таблица очередей организации (название, префикс, статус-бейдж,
  «ожидают») с инлайн-селектом статуса в каждой строке (`open`/`paused`/`closed` —
  `PATCH .../queues/{id}`). Создание и редактирование — общая модалка `QueueFormModal`: название,
  префикс, геозона (широта/долгота/радиус — валидация «все три или ни одного» зеркалит
  `validate_geo_fields` на бэкенде, `lib/geoValidation.ts`), лимит талонов в день, минуты на
  «я здесь». Отдельный нюанс: `presence_timeout_min` в БД `NOT NULL`, а бэкенд-схема `PATCH`
  формально разрешает передать `null` (что уронит запрос в 500 при флаше) — форма никогда не
  отправляет `null` для этого поля, только либо число, либо не включает поле вовсе (оставить как
  есть).
- **`/admin/queues/:id/schedule`** — 7 строк (пн…вс), чекбокс «рабочий день» +
  `opens_at`/`closes_at`, предзаполняется из нового `GET .../schedule`, сохраняется через
  `PUT .../schedule` (дни без чекбокса просто не попадают в массив — значит выходной, как и
  задумано в `queue_schedules`).
- **`/admin/cabinets`** — таблица кабинетов (название, очередь, статус-бейдж
  free/busy/paused/offline). Создание — `CabinetFormModal`: label + переключатель
  «создать очередь автоматически» / «использовать существующую» (ровно то же поведение, что
  бэкенд уже даёт при `queue_id: null`, никакой новой логики). Кнопка «Операторы» открывает
  `CabinetOperatorsModal` — список назначенных (из нового `GET .../operators`) с кнопкой «Убрать»,
  плюс выпадающий список активных операторов организации, которых ещё нет в кабинете, с кнопкой
  «Добавить».
- **`/admin/users`** — таблица персонала (имя, email, роль, статус). Создание —
  `StaffFormModal` (имя, email, пароль, роль operator/registrar — без бэкенд-несуществующих
  ограничений на пароль, схема на бэкенде не требует минимальной длины, форма не выдумывает
  свою). Деактивация/активация — одна кнопка, переключает `is_active` через тот же `PATCH`, без
  удаления записи.

Общее для всех трёх: любая ошибка от бэкенда (`404`/`409`/`422`) идёт через уже существующий
`useToasts()`/`ToastStack` (как в `/operator`), текст — через новый `lib/apiError.ts:
apiErrorMessage()`, который сопоставляет HTTP-статус с локализованным сообщением
(`admin.errors.notFound/conflict/invalid/unknown`) — не голый JSON и не сырой `code` из бэкенда
(большинство 404/409 в admin-CRUD — обычные `HTTPException` с нелокализованной строкой, а не
`ServiceError` с чистым `code`, поэтому сопоставление по статусу, а не по строке).

Новые строки — `admin.queues.*`, `admin.schedule.*`, `admin.cabinets.*`, `admin.users.*`,
`admin.errors.*` — на kk/ru/en. Новый переиспользуемый `components/StatusBadge.tsx` вместо
page-specific классов для статусов очереди/кабинета/сотрудника.

## Ручной сквозной тест

Тестов фронта нет (и не было раньше) — проверено вручную прямыми HTTP-запросами с теми же
payload'ами, что реально отправляют формы (см. `git log` этого шага для точного скрипта), плюс
визуально через `docker compose up`:

1. Войти **org_admin** → `/admin/queues` → «Создать очередь»: название «Терапевт», префикс `A`,
   геозона (широта/долгота/радиус все три), лимит в день, минуты на «я здесь» → очередь в списке
   с «Ожидают: 0».
2. У этой очереди — «Расписание» → отметить пн/вт/ср рабочими, 09:00–18:00 → «Сохранить
   расписание» → перезайти на страницу — дни всё ещё отмечены (предзаполнение через новый `GET`).
3. `/admin/cabinets` → «Создать кабинет»: название «Окно 7», «Создать новую очередь
   автоматически» → в списке кабинет со своей (новой) очередью, статус «Не в сети» (пока не
   выбран оператором).
4. У этого кабинета — «Операторы» → создать через `/admin/users` оператора, если ещё нет →
   выбрать его в выпадающем списке → «Добавить» → появляется в списке назначенных.
5. `/admin/users` → «Добавить сотрудника»: роль «Регистратор» → создаётся, статус «Активен».
6. У регистратора — «Деактивировать» → статус меняется на «Деактивирован» (запись остаётся,
   не удаляется — как и оператор с ролью, который просто перестал бы логиниться при той же
   кнопке).
